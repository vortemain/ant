# Plan, milestones, and decisions

## Current status

As of 2026-11-14 (working tree; last commit `ec1d845`, the D-029–D-034 work is not yet committed): P1 (front door), P2 (speed engine, measured), P4.1–P4.2 (Gradle/Android adapter, shared Gradle task cache) and P3.1–P3.4 (local change detection, local result reuse in `ant build`, faster restores via hard-link, path-independent release keys) are done; decisions run through D-035. Cheaper plan generation via a `cargo metadata` cache (D-031) is done — on a cache hit the ~0.3–0.4 s `cargo metadata` call is skipped entirely. Parallel plan generation (D-032) is done — `cargo --version` and `toolchain_digest` now overlap with manifest/lock digesting via `std::thread::scope`; measured on this repo: `ant build` no-change 0.23 s vs `cargo build --release` no-change 0.70 s (3× faster). Warm local Gradle builds (D-033) are done — `ant build` keeps Gradle's daemon between local builds (adapter `daemon` option + the `_ANT_DAEMON` marker; on Windows the direct executor lets a marked action's daemon outlive the action; `ant.toml` `[options] daemon = "0"` restores the hermetic one-shot), verified locally by unit tests and a stub-wrapper e2e; the JetNews edit-loop number is still unmeasured. Path-independent dev-profile reuse (D-034) is done — a second clone restores from the first clone's cache and the artifacts are byte-identical — and the Rust local edit loop is measured at parity (dev one-file edit 28.6 s vs cargo's warm incremental 27.6 s; post-D-034 addendum in `docs/benchmarks/2026-11-14-local-rust.md`). The install-by-QR encoder (D-035, P4) is done — `ant qr [TEXT]` renders a terminal QR from a zero-dependency, unsafe-free module (byte mode, level M, versions 1-10) proven three ways: format/version strings asserted against the published table, every matrix decoded by the independent jsQR decoder (`scripts/qr/verify-qr.js`, all 8 forced masks plus real payloads), and the forced-mask-4 rendering bit-identical to the production qrcode-generator reference (zero-module diff); the remaining P4 piece is signing — encrypted keystore management and a signed APK/AAB from `ant build android`. The active phase is **P3 Local-first speed** (D-026): what remains is measurement debt — the JetNews warm-daemon number (needs the Android SDK; the `bench-android` CI run), a second repository and machine before ratios are quoted as expected values, and npm/Gradle cache measurements on Windows — then P4 signing (encrypted keystore, signed APK from `ant build android`). The prioritized next-action list with acceptance criteria, the measured numbers, and known gotchas are in `AGENTS.md` ("Start here"). The milestone table and task ledger below remain the engineering record; older ledger rows describe the state at the time they were written.

## Product roadmap (2026-11-13, decision D-016 — read `docs/vision.md` first)

The owner's vision is a Bun/Expo-class tool that covers **everything**: every platform and language, few commands, very fast, **local-first** (D-026: most developers build on their own laptop; servers are an optional extension), with a polished dashboard. The phases below order that work by dependency; each phase ends in something a developer can use. The M-milestone table that follows remains the engineering record of what exists; this roadmap decides what comes next.

| Phase | Outcome a developer gets | Builds on | Exit criteria |
|---|---|---|---|
| P1 Front door | `ant init` / `ant build` with zero required configuration: detect the project, pick the adapter, build, package into `dist/`, reuse what is provably reusable; a minimal `ant.toml` only when needed; plumbing commands stay for power users | adapters, plans, local executor, cache | a Rust, an npm, and a CMake project each build with `ant build` alone; clear errors; docs show only the short commands — **met on Windows (2026-11-13, P1.1)**; deliverables are collected for Rust only so far (npm/CMake outputs stay where their tools write them); the Linux build and full test suite pass in CI since P2.1, but `ant build` has not yet been exercised on Linux by hand |
| P2 Fast real builds | real projects actually hit the cache: dependency sources declared (lockfiles, vendored/fetched sources digested), cheap isolation check, the Linux build compiling and tested | P1, cache, sandbox | measured cold/warm/no-change numbers on real projects against the native tool (cargo/npm/Gradle), on Windows and Linux — **Linux/cargo measured (P2.5–P2.6): fresh checkout ≈0.6 s via the shared cache vs ≈25 s plain cargo; cold 33 s vs 24 s (batched transfers)**; Windows and npm/Gradle not yet measured |
| P3 Local-first speed (D-026) | `ant build` is fast on the developer's own machine with no server: a local result cache on by default where results can be proven, laptop-side work proportional to what changed (metadata-cached digests), warm local reuse for the edit loop, Android/Gradle through `ant build` | P2 | measured on real projects (Rust, npm, Android) on an ordinary laptop: no-change and fresh-clone builds far faster than the native tool, edit loop at least as fast |

| P9 Ship and run | store submission (Play/App Store), over-the-air updates and an Expo Go-style live preview, enterprise (SSO, audit, policy) | P4–P8 | each feature end to end with docs |

## Decision log

### D-001: Start with contracts and one Rust workspace
**Status:** Adopted provisionally. Cargo workspaces support shared metadata and commands; crate boundaries should follow stable responsibilities. Source: [Cargo workspace reference](https://doc.rust-lang.org/cargo/reference/workspaces.html). Keep the initial member count small. Revisit after first vertical slice.

### D-002: Treat REAPI as an interoperability target, not the internal domain model
**Status:** Adopted provisionally. The upstream project describes a set of APIs for input upload, execution, monitoring, and content-addressed caching. Mapping at the remote boundary keeps local semantics independent. Source: [Bazel Remote APIs repository](https://github.com/bazelbuild/remote-apis). Exact feature/conformance scope remains open.

### D-003: Default actions to non-cacheable
**Status:** Adopted. Correctness and secret isolation require conservative behavior when declared inputs or hermeticity are incomplete. **Addendum (2026-11-13, T2.8):** the letter changes from "unwired in the run path" to "wired behind the blocker gate" — `ant run --plan --cache-dir` now computes the action-key candidate from pre-run digests and stores/looks up only when the candidate reported no blockers. The gate's spirit is unchanged and stronger-tested: every executor still reports `network-isolation-unavailable` (D-009), so `cache_eligible` is false for every real key and nothing is reused; an end-to-end test proves a fully-declared action writes no cache entries. Cache failures degrade to misses/warnings, never to trusting unverified content. **Addendum (2026-11-13, T2.10):** the gate now opens for exactly one executor, `--network-isolated` (D-013); reuse is proven end to end there and remains impossible under every other executor.

### D-034: Path-independent keys and outputs for dev builds
**Status:** Adopted 2026-11-14 (P3.8). Dev builds embed absolute source paths (debug info) and incremental-compilation codegen-unit names derived from a session id, so D-030 could not cover them: two clones of one project built different bytes and hashed different keys. The cargo adapter now makes every dev action carry the path-independence marker plus two settings: `CARGO_INCREMENTAL=0`, and `CARGO_ENCODED_RUSTFLAGS` joining `--remap-path-prefix` flags for every spelling of the workspace root (verbatim `\\?\`, plain, forward-slash) mapped to the fixed token `/ant-workspace` — so two clones produce byte-identical binaries. On the key side, `action_key_candidate` (with the marker present) additionally normalizes environment *values*: every spelling of the workspace path inside a value is replaced by `<workspace>`, because the remap flags themselves name this clone's absolute root and would otherwise defeat the excluded workspace path. Any other byte difference in a value survives normalization, and the marker keeps path-independent and path-dependent keys in separate domains (D-030). npm and CMake stay path-dependent on purpose (npm: the build script is user code that may embed absolute paths; CMake: `CMakeCache.txt` — the declared configure output — embeds the absolute build path), documented in `docs/cli/adapters.md`. Verified by `build-digest` unit tests (multi-spelling value normalization; dev-style remap values hash equal across folders while different flag sets still differ) and end to end by `ant-cli/tests/path_independence.rs`: two clones in different folders sharing one `ANT_CACHE_HOME`, the second clone's `ant build --dev` restores the first's results and the artifacts are byte-identical. Honest limits: user code using `env!("CARGO_MANIFEST_DIR")` or `file!()` can still bake the path in; `CARGO_ENCODED_RUSTFLAGS` overrides `[build] rustflags` in the project's `.cargo/config.toml` (not merged); `CARGO_INCREMENTAL=0` overrides `build.incremental`. Measured cost of giving up incremental compilation on the local edit loop: parity, not regression — same-day A/B after the change (`docs/benchmarks/2026-11-14-local-rust.md` addendum): one-file edit 28.6 s vs cargo's warm incremental 27.6 s (0.96×), because the workspace action rebuilds the edited crate and dependents either way.

### D-035: Install by QR with a minimal zero-dependency QR encoder
**Status:** Adopted 2026-11-15 (P4). The install-by-QR flow needs a QR code of the
download URL, and a build tool should not pull a QR crate (or its transitive
`gltf`/`image`/`num-bigint`) into a workspace pinned to a tiny, audited
dependency set. `crates/ant-cli/src/qr.rs` is a zero-dependency,
`unsafe_code = "forbid"`-clean byte-mode encoder (ECC level M, versions 1–10,
213-byte payload cap at version 10), surfaced as `ant qr [TEXT]`. It is proven
three independent ways: unit tests against the published format/version/RS
generator-polynomial tables, an external decoder (`scripts/qr/verify-qr.js`,
jsQR, 12 dump matrices) and a bit-for-bit zero-module diff against the
production `qrcode-generator` reference. Two real bugs surfaced (a doubled
mask bit and the zig-zag column-pair ordering) and are now covered. Full ADR:
`docs/adr/0004-install-by-qr-with-a-minimal-zero-dependency-qr-encoder.md`.

### D-036: Release signing — sealed keystores, secrets by digest, never by value
**Status:** Adopted 2026-11-15 (P4). `ant keystore import` stores one Android
signing keystore per project in a per-user directory keyed by the project's
canonical path; the keystore file keeps its own Java-encrypted form, and its
passwords are sealed by AES-256-GCM under a key derived from a master
passphrase with PBKDF2-HMAC-SHA256 (600_000 iterations, OWASP 2023), read from
`ANT_SIGNING_PASSPHRASE` or a terminal prompt. Passwords never travel through
argv: `keytool` reads them from the child environment, and a build hands them
to Gradle as build-time-only environment variables in the spawned process —
never in the plan file, the action key, the event stream, or any cache. The
plan references the keystore only by content digest (`sha256:…`), so a
different keystore is a different action key while revealing nothing. The
Gradle adapter stamps the signing marker env and writes an init script so the
release task picks up the keystore; `ant build --release` resolves the secrets
before the run and injects them only into the matching plan, and a stale
plan/keystore mismatch fails closed. Verified: `signing.rs` unit tests
(seal/open round-trip, wrong-passphrase message names the cause, keystore
digest verify, no-plaintext in entry metadata, per-project store scoping), the
Gradle adapter sign-option tests (marker env, init script, release-only), and
a `cache_runner` stub end-to-end test that the secrets reach only the matching
plan and never a cache.

### D-037: Install by QR — serve collected release APKs on the LAN
**Status:** Adopted 2026-11-15 (P4). After `ant build --release` collects signed
APKs into `dist/`, the front door binds a short-lived HTTP server
(`crates/ant-cli/src/serve.rs`, `tiny_http`) on all interfaces at an
OS-assigned port, prints the QR code (D-035) of `http://<lan-ip>:<port>/<file>`,
and serves exactly the collected `.apk` files — nothing else — until Ctrl+C.
`--no-serve` opts out; when stdout is not a terminal the QR cannot render, so
serving is skipped. The QR carries only the URL: no token, no path traversal,
no directory listing — a request for anything but an exact collected file name
is a 404. Verified by `serve.rs` loopback HTTP end-to-end tests (serves the
exact collected name, refuses everything else, routing) and the QR module
tests; the LAN-address helper reports an address even when offline.

### D-031: Cheaper plan generation — `cargo metadata` cache
**Status:** Adopted 2026-11-13 (P3). `cargo metadata` (the dependency-graph resolver invoked during plan generation) costs ~0.3–0.4 s per run — the dominant remaining cost on a no-change build. A per-user cache (`<user cache>/cargo-metadata.json`, `ANT_CACHE_HOME` overrides) stores the parsed JSON keyed on the canonical workspace root, adapter options, `cargo --version` output, the cargo executable's SHA-256 digest, and content digests of every `Cargo.toml` and `Cargo.lock` the project contains. On a cache hit the `cargo metadata` call is skipped entirely; the tree walk (`declare_project`) still runs on every invocation, so new, removed, or modified project files are detected. Any cache problem (missing file, stale entry, unreadable manifest, changed lock, different toolchain) falls back to a live `cargo metadata` call. The cache is best-effort write (failures are silently ignored — the next run re-runs `cargo metadata`). `cargo --version` still runs on every invocation as the toolchain-identity safety net (a binary replaced with identical size and preserved mtime is not re-hashed by the toolchain digest cache). Measured by 6 new `build-adapter` unit tests: round-trip hit, manifest-change miss, options-change miss, toolchain-change miss, lock-change miss, and same-key replacement.

### D-032: Parallel plan generation — overlap `cargo --version` with manifest digesting
**Status:** Adopted 2026-11-13 (P3). After the metadata cache (D-031) eliminated the ~0.3–0.4 s `cargo metadata` call on a cache hit, the remaining plan-generation cost was `cargo --version` (~0.1 s process spawn) and manifest/lock file digesting (~0.05–0.1 s I/O), run sequentially. `generate` now uses `std::thread::scope` to run `cargo --version`, `toolchain_digest`, and `prepare_metadata_cache` (the cache-file read + manifest/lock re-digesting) in three parallel threads, then joins them and calls `verify_metadata_cache` (the key comparison, which needs all three results). The `try_metadata_cache` function is split into `prepare_metadata_cache` (I/O-heavy, no toolchain identity needed) and `verify_metadata_cache` (toolchain identity + digest comparison); `try_metadata_cache` remains as a `#[cfg(test)]` convenience wrapper so existing tests pass unchanged. Measured on this repository (Windows, release): `ant adapt` warm 0.20 s vs `cargo metadata` 0.40 s; `ant build` no-change 0.23 s vs `cargo build --release` no-change 0.70 s (3× faster, meeting the "≤ cargo's own no-change time" acceptance criterion).

### D-033: Warm Gradle daemon for local builds
**Status:** Adopted 2026-11-13 (P4). Android's edit-loop loss (one-file edit 72.6–74.2 s vs Gradle's warm incremental 2.0–3.3 s, the remaining `AGENTS.md` next-action) is dominated by Gradle re-paying daemon and startup costs inside a fresh worker workspace: the adapter always passed `--no-daemon`, and on Windows the direct executor's kill-on-close job object would have terminated a daemon anyway. Three coordinated changes: (1) the Gradle adapter accepts a `daemon` option (values 0|1, default 0 = the hermetic one-shot); `1` drops `--no-daemon` and stamps `build_digest::DAEMON_MARKER` into the action environment — since `action.environment` is hashed into the key, the daemon and hermetic variants never share a cache entry; (2) `ant build` defaults `daemon = "1"` for adapters that accept it, `ant.toml` `[options] daemon = "0"` opts out, and `ant adapt` plans stay hermetic because a sandboxed or remote run gains nothing from a daemon a later run cannot reach; (3) the Windows direct executor skips the kill-on-close job for marked actions — a memory-capped action keeps the job (the cap cannot be enforced without it) — so the daemon survives the action exactly as when a developer runs Gradle directly; non-Windows direct execution attaches no job, so nothing changes there. Verified locally (Windows): six new unit tests (adapter daemon argv/marker, hermetic default with 0|1 validation, marker-separated keys, front-door default on and opt-out, an unmarked action's detached grandchild killed by the job, a marked action's surviving it) and a new e2e (`ant-cli/tests/gradle_daemon.rs`): the wrapper's recorded command line has no `--no-daemon`, `_ANT_DAEMON=1` reaches the action, the daemon's home lives under `.ant/`, and `daemon = "0"` restores the hermetic variant with the APK still collected. `benchmarks/android/run.sh` gained an `ant-build-one-file-change` row (front door, warm daemon, local reuse missing) for the next benchmark run. Not yet: a measured JetNews edit-loop number with the daemon warm (needs an Android SDK locally or the benchmark runner).

### D-030: Path-independent action keys for release builds
**Status:** Adopted 2026-11-13 (P3). Release builds (`cargo build --release`) do not embed debug info by default, so their outputs do not contain the absolute workspace path. The cargo adapter places a `build_digest::PATH_INDEPENDENT_MARKER` environment variable on the action; `action_key_candidate` sees it and excludes the workspace path from the key, so a second clone of the project in another folder restores instead of rebuilding. The marker itself is hashed into the key (it is part of `action.environment`), which keeps path-independent keys from colliding with path-dependent ones. Dev builds (the default) keep the workspace path in the key because Rust embeds absolute source paths in debug info. User code using `env!("CARGO_MANIFEST_DIR")` can still embed the path; that is a documented limitation. Measured by two new `build-digest` unit tests: path-dependent by default, path-independent when the marker is present, and the two domains never collide. **Addendum (2026-11-14, D-034):** dev builds are now path-independent too (remapped `--remap-path-prefix` flags, `CARGO_INCREMENTAL=0`, and normalized environment values) — see D-034 and row P3.8.

### D-029: Restores hard-link outputs from the store, and re-runs break the link first
**Status:** Adopted 2026-11-13 (P3). `build-cache` restore copied ~70 MB of outputs back into the workspace on every cache hit, so "switch back to built code" was bounded by copy bandwidth. Restore now prefers a hard link from the content-addressed blob into the workspace (instant when the cache and workspace share a volume) and falls back to `copy` when the link fails (cross-volume). The restore-time re-digest of every restored file still runs either way, so a corrupted blob is still a miss, never trusted content. Hard-linking reintroduces two hazards, both closed by clearing the action's declared outputs from the workspace *before* re-running it on a cache miss (in `cache_runner::run_action`, only when a cache is open): (1) a sandboxed/network-isolated action runs as a restricted account that cannot overwrite a file whose inode lives in the user-owned cache store — it failed with "Access is denied" — and (2) an in-place rewrite of a hard-linked output would corrupt the shared, content-addressed blob, silently degrading the cache on every edit cycle. Removing the outputs first lets the action regenerate fresh files (the blob keeps its link and its content) and is correct because a cache miss means the declared outputs are stale by definition; the reuse path is untouched. Measured on the network-isolated cache e2e: store → reuse-with-restore → invalidate-on-input-change → rebuild all pass; two new `build-cache` unit tests prove a restore hard-links on the same volume and that a stale pre-existing output is replaced. Not yet: `reflink` (copy-on-write) on filesystems that support it but disallow hard links (rare for same-volume stores), and a measured restore-time number on this repository (the ≤ 1 s target in `AGENTS.md` next-action #1).

### D-028: `ant build` reuses this machine's own results (local trust, like Turborepo)
**Status:** Adopted 2026-11-13 (owner chose "Yes, like Turborepo"). Proof-based reuse (sandbox + network isolation) stays the only way results are *shared*; on top of it, plain `ant build` now reuses results **built on the same machine** without a sandbox. A new plan policy `cache_policy: local` means every output-affecting input is declared or pinned but some pinned content lives outside the project: cargo plans with a `Cargo.lock` whose non-member packages are registry/git (lock-pinned) or inside the project (path dependencies outside the project stay `never`), and Gradle plans without in-project dependencies. Keys use content-only digests (a branch switch or re-checkout that rewrites timestamps still hits) and the normal key material (argv, env, toolchain identity, platform, workspace path), then are domain-separated (`build_digest::trusted_local_key`): only the blockers no-sandbox, no-network-isolation, content-only digests, and local-only policy are accepted; `never` policy, a missing toolchain identity, or input-digest mismatches still block. Results go to a separate per-user store (`<user cache>/local-results`) that is never uploaded or shared. Actions without declared outputs (npm by default, CMake) are not reused. `ant build --fresh` skips lookups (and refreshes the stored result). Restores skip outputs already in place with the right content (checked through the change-detection cache). **Accepted risk:** a build that reads an undeclared, unpinned input could be reused stale on this machine; `--fresh` is the escape hatch. Measured on this repository (Windows, debug): switching back to previously built code 2.7–4.5 s vs cargo 10.0–11.0 s; nothing changed 0.55 s vs cargo 0.45 s.

### D-027: Change detection, absolute temp dirs, and one cargo invocation for `ant build`
**Status:** Adopted 2026-11-13 (P3.1). (1) Developer commands (`ant build`, `ant run`, `ant remote run`) keep a per-workspace change-detection cache in the per-user cache directory (never in the workspace, so it can never become an input): a file's digest is reused while its size, modification time, and change marker (inode+ctime on Unix, creation time on Windows) are unchanged and the entry was recorded at least 2 s after the modification (git's racily-clean guard). Workers never enable it. `ANT_NO_DIGEST_CACHE=1` turns it off. Trust model: same as make/git. (2) Plans keep declaring `TMP`/`TEMP`/`TMPDIR` workspace-relative (path-independent keys), but executors make relative values absolute against the action's working directory at spawn time: cargo build scripts run in other directories and the MSVC linker failed with LNK1104 under `ant build` on Windows (a pre-existing bug found by running `ant build` on this repository). (3) `ant build` asks the cargo adapter for `granularity=workspace` by default: one `cargo build --workspace` instead of one invocation per member (cargo parallelizes crates itself; a no-change build paid cargo's startup per member). Measured on this repository (Windows, debug, nothing changed): `ant build` 4.8 s → 2.9 s (change detection) → 1.2 s (one invocation); plain `cargo build` 0.45 s; the rest is plan generation (`cargo metadata` + `cargo --version`, ≈0.5 s), deliberately not cached because a rustup toolchain switch does not change the cargo shim's file stamp.

### D-026: Ant is local-first; servers are an optional extension
**Status:** Adopted 2026-11-13 (owner's direction). Most developers have no VPS and build on their own, often old, laptop. Ant's product, roadmap, branding, and docs lead with fast local builds; remote/VPS execution (coordinator, workers, shared remote cache, `ant server deploy`) is an optional extension and moves to P8. The next phase (P3) is local-first speed: a local result cache by default where results are provable, laptop work proportional to changes, warm local reuse for the edit loop, and Android through `ant build`. The remote engine already built stays; its measured wins (shared cache, task cache) carry over to local reuse. Logo tagline, README, and the GitHub description were updated to match.

### D-025: Gradle's task cache is served by the coordinator, written only by workers
**Status:** Adopted 2026-11-13 (P4.2). On an Ant cache miss the worker starts from an empty workspace, so every edit was a full Gradle build. Workers started with `ant worker --sandbox --task-cache` (Linux only) now serve Gradle's HTTP build cache to actions declaring `ANT_GRADLE_TASK_CACHE=1` (the Gradle adapter does so for cache-eligible plans, with `--build-cache`): a host-side Unix socket per job forwards `GET`/`PUT /cache/{key}` to `/v1/task-cache/gradle/{key}` with the worker's token; the socket's directory is bound into the sandbox, where `ant __gradle-cache-bridge` listens on the sandbox loopback, writes an init script into `$GRADLE_USER_HOME/init.d`, and runs the action. The token never enters the sandbox and the sandbox gains no other network. Clients and viewers cannot write entries. **Trust:** any build that runs on a worker can write any Gradle key, so the task cache trusts every project the workers build: right for one owner's servers, not for a multi-tenant service (would need per-tenant namespaces). Cache-eligible Gradle plans no longer pass `--offline` because Gradle disables its remote cache in offline mode; the no-network sandbox still fails a missing dependency. Measured on JetNews (run 43474904549): one-file edit 72.6–74.2 s (18/36 tasks from cache) vs ≈150 s before; Gradle's warm incremental edit is 2.0–3.3 s.

### D-024: Gradle/Android builds are cacheable only with in-project dependencies
**Status:** Adopted 2026-11-13 (P4.1). The `gradle` adapter runs one wrapper task per project with the whole project (minus `build/`, `.gradle/`, IDE and Ant dirs) as input and each application module's debug APK as output. Gradle fetches dependencies and its distribution from the network, so the action is cache-eligible only when both are project inputs: `.gradle-deps/` (a read-only copy of `caches/modules-2`, passed as `GRADLE_RO_DEP_CACHE`) and a local `distributionUrl`; it then runs `--offline`, Kotlin in-process, with Gradle's and Android's homes inside the workspace. `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT` join the Unix environment allowlist as key material; the JDK and SDK themselves are not digested (accepted gap, documented). Measured on JetNews (run 43465528849): cold 159 s vs Gradle 157 s; unchanged/fresh checkouts 0.65–0.86 s vs Gradle (warm daemon + build cache) 1.6–4.6 s.

### D-023: Blobs move in verified batches
**Status:** Adopted 2026-11-13 (P2.6). Cold remote builds of Ant itself cost ~255 s against ~30 s for cargo because 6,430 files moved one HTTP request each. `POST /v1/blobs/batch-put` and `batch-get` carry many blobs per request in a length-prefixed framing (≤ 1024 blobs, senders split at ~32 MiB) without weakening any guarantee: every blob is re-hashed, one bad blob rejects a whole upload batch with nothing stored, downloads never return partial sets, viewers are refused. Measured: cold 33.3 s vs cargo 24.3 s in the same run (transfer overhead ~225 s → ~7 s). Single-blob routes stay for small transfers and compatibility.

### D-022: Remote cache keys are computed before inputs are downloaded; files carry the executable bit
**Status:** Adopted 2026-11-13 (P2.5). The first full benchmark showed cache hits on Ant itself costing ~216 s because the worker materialized all inputs before consulting the cache. The worker now derives the key from the job's own entries (`build_digest::digest_tree_from_entries`, proven equal to `digest_tree`), fetching only root-level files so `--version` honors toolchain pins; hits return without further downloads, and on a miss the files on disk must hash to the same key before the result is stored. Separately, transferred files carry an `executable` flag (protocol `Entry`, default false, not part of keys) restored on the worker and on install — remote-built Linux binaries were not executable. Measured effect: hits went from ~216 s to ~1.1 s (`docs/benchmarks/2026-11-13-remote-cache.md`).

### D-021: A cargo build's input is the whole project (minus outputs and metadata)
**Status:** Adopted 2026-11-13 (P2.4), after remote execution exposed two undeclared inputs: building one package makes cargo load the whole workspace (every member manifest, target-inference files, every locked dependency's manifest), and Rust code can read any project file at compile time (`include_str!`, build scripts — Ant's own crates do). Every cargo action therefore declares the whole project top-down except the target directory, `.ant/`, `.git/`, and output directories Ant created; a symlink keeps the plan uncacheable; files outside the project remain undeclarable and fail closed remotely. Consequence: any file added to the project changes the key (it could be read). A new option `granularity=workspace` emits one `cargo build --workspace` action, which compiles dependencies once — the right shape for remote jobs. This also corrected earlier per-member local keys, which were incomplete.

### D-020: Fully declared cargo builds are cacheable; workers key on their own toolchain
**Status:** Adopted 2026-11-13 (P2.4). The cargo adapter marks actions `cache_policy: eligible` exactly when every non-member package lives inside the project (vendored or path) and `Cargo.lock` exists; such actions pin a workspace-local `CARGO_HOME` so undeclarable user-level cargo config cannot change them. `rust-toolchain(.toml)` is an input. Remote workers replace the plan's client-observed toolchain identity with the toolchain they actually run (argv[0] resolved on the worker's PATH: cached digest + `--version` in the workspace, digest alone for tools without `--version`); unresolvable programs keep the action out of the cache.

### D-019: Shared remote cache — proven on sandboxed Linux workers, path- and time-independent keys
**Status:** Adopted 2026-11-13 (P2.3). Remote cache keys must match across jobs, checkouts, and machines, but local keys include the workspace path and input modification times. Rather than weakening local keys, the worker controls its environment: it writes every input with a normalized mtime (so metadata is a deterministic function of content) and mounts each workspace at a fixed in-sandbox path (`/tmp/ant/ws`, via `PreparedAction::sandbox_mount`), which makes content-only input digests a complete key (`ExecutionFingerprint::remote_worker_sandboxed`). Only sandboxed Linux workers (D-018: no network, write-confined) may store entries, and only for blocker-free keys; clients and viewers can never write, so client compromise cannot poison the cache, while worker hosts and tokens are trusted (documented). The lookup happens on the worker before executing, so the same job can be satisfied without running. Local (non-remote) keys keep path and mtime sensitivity; reusing local results across checkouts is not claimed.

### D-018: Linux sandbox = bubblewrap with every namespace unshared; it may declare network isolation
**Status:** Adopted 2026-11-13 (P2.2), following the owner's choice to keep proof-based reuse and get speed from Linux workers. On Linux, `--sandbox` runs actions under bubblewrap (`--unshare-all --die-with-parent --new-session`, read-only `/`, private tmpfs `/tmp`, fresh `/dev`/`/proc`, the workspace bind-mounted read-write). The empty network namespace blocks connections and name resolution alike — stronger than the Windows account mode (D-013, where DNS leaks) — so this executor declares `sandboxed` and `network_isolation` (`ExecutionFingerprint::local_namespace_sandboxed`, chosen per platform by `local_executor::sandboxed_fingerprint`) and opens the cache gate with no elevated setup. bubblewrap was chosen over hand-written namespace FFI (the workspace forbids `unsafe`) and over containers (image lifecycle, startup latency): it is a small, widely deployed setuid-free tool (Flatpak's sandbox). A per-process preflight proves the sandbox can be created and fails closed with actionable advice (missing package; Ubuntu's AppArmor userns restriction). Accepted limits: host reads are not confined (the network is), the kernel is shared, memory caps remain Windows-only. Workers on Linux therefore produce provable results cheaply — the basis for the shared remote cache (next P2 slice).

### D-017: Front-door behavior for `ant build` / `ant init`
**Status:** Adopted 2026-11-13 (P1.1). `ant build` is zero-configuration: detection picks the adapter (ambiguity is resolved once with `ant init --adapter`, never guessed), plans are generated in memory and kept at `.ant/plan.json`, all cores are used, and progress is rendered for humans from the event stream while the engine's `key=value` lines stay available behind `--verbose` (and unchanged under `ant run`). Builds are **release by default** (`--dev` for debug) because the product's purpose is producing shippable output. Deliverables are chosen by each adapter (`BuildAdapter::artifacts`: cargo binaries, not intermediates; nothing is claimed where the adapter cannot know, e.g. CMake targets) and copied into `dist/`, which Ant only writes when it created it (marker file) — user files are never overwritten. `ant.toml` is optional, parsed with the `toml` crate (1.2; the format developers already use for Cargo and Bun), strict about unknown keys. Toolchain identity digests are cached per user by path/size/mtime (`toolchains.json` in the user cache directory): re-hashing `node.exe` (85 MB) cost ~6.6 s per build and dominated plan generation; the trade-off (a binary replaced with identical size and preserved mtime is not re-hashed) is the same as make's and is documented.

### D-016: Product vision drives the roadmap — front door first, then speed, self-hosting, mobile
**Status:** Adopted 2026-11-13 at the owner's direction (`docs/vision.md`: "the vision is having everything covered"). Batches A–E built a sound engine (action model, cache, sandbox, remote protocol, read-only dashboard) but exposed it as plumbing (`ant adapt … --out plan.json`, `ant run --plan … --cache-dir …`), and real projects never hit the cache. Work is re-ordered into product phases P1–P9 (see "Product roadmap"): a zero-configuration front door (`ant init`, `ant build`) first, then proven speed on real projects including the Linux build, then one-command self-hosting, then Android and iOS (iOS requires Mac workers — a hard platform constraint), then every other ecosystem, a product-grade dashboard, scale, and shipping/runtime features. Engine work continues only where a phase needs it. The trust rules in `AGENTS.md` are unchanged: speed is measured, reuse is proven, nothing is called supported before it works end to end.

### D-015: The first GUI is a dashboard served by the coordinator itself
**Status:** Adopted 2026-11-13 (T5.1). The first M5 surface is a static, dependency-free HTML/CSS/JS dashboard embedded in the coordinator binary and served from the same origin as its API, instead of a separate desktop app or a JavaScript build toolchain: there is exactly one source of truth (the coordinator's read model), no fabricated or sample data can enter the page, and same-origin serving allows a strict Content-Security-Policy (`default-src 'none'`, scripts/styles/connect only from self, no framing). Access uses a new optional read-only **viewer** role so visibility can be shared without granting submit/upload/lease rights; the token lives only in the browser tab's session storage. Accepted limits: polling (3 s) rather than push, read-only, history limited to coordinator memory, no local-run (event stream) view yet. ### D-014: Remote execution v1 — own minimal protocol, synchronous HTTP, TLS at a proxy
**Status:** Adopted 2026-11-13 (T4.1–T4.3). Ant's remote mode uses its own small, versioned JSON-over-HTTP protocol (`docs/remote/protocol-v1.md`) instead of REAPI for now: the canonical action contract travels unchanged, inputs are exactly the declared set, and blobs are named by Ant's canonical file digest, so remote and local results are directly comparable. REAPI stays an interoperability target (D-002). Dependencies: `tiny_http` 0.12 (synchronous server; matches the workspace's synchronous design and keeps the coordinator small) and `ureq` 3.5 (synchronous client with rustls/ring TLS for `https://` coordinators). The coordinator itself does not terminate TLS: it binds loopback by default and requires `--allow-non-loopback` for anything else, and clients refuse plain-HTTP tokens to non-loopback hosts — TLS belongs to a reverse proxy (operations guide). Accepted v1 limits: in-memory jobs, no log transfer, no cancellation propagation, no routing, no blob GC, sequential client. Revisit an async stack, persistence, and REAPI mapping before M6.

### D-013: Network isolation by dedicated sandbox account; the cache gate opens only under it
**Status:** Adopted 2026-11-13 (T2.9–T2.10), implementing D-009 option A. A one-time elevated `ant sandbox setup`, run by the machine owner, creates `AntSandboxOffline` and block-all firewall rules scoped only to its SID; the password exists only as a current-user DPAPI blob. `--network-isolated` re-verifies the whole setup before every run (fail closed), launches Ant's own runner as the account through Secondary Logon (`CreateProcessWithLogonW`; a non-elevated caller cannot use `CreateProcessAsUserW` with another user's token), suspended until it is job-confined, and the runner restricts its own token so write confinement is unchanged. Only this executor declares `network_isolation` (`ExecutionFingerprint::local_network_isolated`), so it is the only one that can produce blocker-free keys and reuse cache entries. **Accepted residual channel:** DNS resolution goes through the system DNS Client service (another account) and is not blocked; reaching data through it requires deliberately crafted DNS tunnelling, which is outside the first-line, non-adversarial threat model of the Windows sandbox (`windows-design.md`). Accepted limits: per-machine network granularity, profile-local toolchains unreadable to the account, ≈5 s verification per run (benchmark T2.11). Revisit before any adversarial or multi-tenant claim, and before M4.

### D-011: Resource requests are admission weights, FIFO-admitted, clamped, and excluded from the action key
**Status:** Adopted 2026-11-13 (T1.17). Actions may declare an optional `resources` request (`cpu` slots, default 1; `memory_mb`, default undeclared). The parallel scheduler treats `--jobs` as CPU-slot capacity and `--memory-mb` as an optional memory budget, and admits ready actions in strict FIFO order — no backfill past a head that does not fit — choosing starvation freedom and predictability over peak utilization (a backfilling policy needs aging or reservations to stay starvation-free; revisit with measured workloads in the benchmark lab). Requests above total capacity are clamped with a printed note rather than rejected, so plans stay portable across machines and `--jobs` values. Requests are promises by the plan author, not measured or enforced limits (runtime enforcement, e.g. job-object memory limits, is a separate future slice). Resources cannot affect outputs and are therefore excluded from the action-key candidate; absent requests are omitted from serialization so existing plans and adapter output are unchanged. **Addendum (T1.19):** `--enforce-memory` (opt-in, Windows) turns a declared `memory_mb` into a hard job-wide cap; without the flag requests remain admission weights. `cpu` is never enforced at runtime.

### D-006: Justified external dependencies for signal and process-tree control
**Status:** Adopted 2026-11-12. `ctrlc` (3.5.2, CLI-only) installs the cooperative Ctrl+C handler because console control handling requires FFI that the workspace forbids (`unsafe_code = "forbid"`). `win32job` (2.1.0, local-executor, Windows-only target) safely manages job objects for descendant cleanup, which likewise has no safe `std` API. Both are small, MIT/Apache-2.0, and scoped to the one crate that needs them; revisit if they are insufficient for remote worker lifecycle management.

### D-007: Truthful platform fingerprinting via `os_info`, and the Windows sandbox approach
**Status:** Adopted 2026-11-12. `os_info` (3.15.0, build-digest) captures the running OS version so the action key records the platform version as a measured fact instead of leaving a permanent blocker; it is the same crate Cargo itself uses for its user agent (83M+ downloads, maintained). Additionally, research into Windows sandboxing (recorded in `docs/sandbox/windows-design.md`) establishes the intended approach: restricted tokens with per-root restricting SIDs plus scoped NTFS ACL grants and job objects — not AppContainer first — with network enforcement treated as a separate open problem because restricted tokens cannot prevent network access for same-user code. A future low-level FFI crate may carry audited `unsafe` only by explicit decision excluding it from the workspace lint inheritance. **Implemented (2026-11-12):** the `ant-sandbox-win` crate realizes this design — `CreateRestrictedToken` with `DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICT`, a deterministic `S-1-5-21-…` capability SID derived from `SHA-256("ant-sandbox-cap-v1\0" || canonical workspace path)`, an idempotent ACL grant on the workspace root (with post-apply verification so FAT/exFAT fail closed), a permissive default DACL, `SeChangeNotifyPrivilege` enabled, `lpDesktop = winsta0\default`, and a kill-on-close job object for descendants — and is wired into `ant run --sandbox`. `ExecutionFingerprint::local_sandboxed` truthfully declares `sandboxed: true` + `metadata_fingerprinting: true`; `network_isolation` stays false, so cache reuse remains gated by D-003.

### D-008: `windows-sys` FFI for `ant-sandbox-win`, with an audited lint-inheritance exception
**Status:** Adopted 2026-11-12. The Windows sandbox is built on the `windows-sys` 0.59 raw FFI bindings (features `Win32_Foundation`, `Win32_Security`, `Win32_Security_Authorization`, `Win32_Storage_FileSystem`, `Win32_System_Threading`, `Win32_System_Console`) — the same bindings the Rust for Windows project ships, with broadest reuse and no third-party security-boundary crate. `zagens-windows-sandbox` (1065 downloads, a single small publisher that ships its own runner binaries) was evaluated and rejected as too immature to trust as a security boundary. `ant-sandbox-win` deliberately does **not** inherit `[lints] workspace = true`, because the workspace-wide `unsafe_code = "forbid"` discipline cannot express the audited FFI boundary this crate owns; every `unsafe` block in the crate carries a `SAFETY` comment and the public API exposed to the rest of the workspace is safe Rust. The crate-level audit contract and honest limitations (this is a first-line write-confinement defense against accidental escape, not a hardened adversarial boundary; world-writable locations remain writable; network stays unrestricted) are documented in `docs/sandbox/windows-design.md`. The design is adapted with attribution from OpenAI Codex `codex-rs/windows-sandbox-rs` (Apache-2.0).

### D-009: Network isolation requires a dedicated sandbox user + elevated setup; keep `network_isolation = false` and the cache gate closed
**Status:** Adopted 2026-11-13. Investigation in `docs/sandbox/network-isolation.md` established with primary-source evidence that: (1) adding WFP filters or firewall rules is administrator-gated (`FWPM_ACTRL_ADD`/`ADD_LINK`; Microsoft docs), so per-run non-elevated enforcement is impossible; (2) the mechanism proven by both shipped Windows sandboxes (OpenAI Codex, `zagens-windows-sandbox`) is firewall/WFP rules scoped by `FWPM_CONDITION_ALE_USER_ID`/`LocalUserAuthorizedList` to a **dedicated local sandbox account** provisioned by an elevated one-time setup, with the child running as that account; and (3) that scope cannot match Ant's restricted-token capability SIDs, because the user SID is unchanged by `CreateRestrictedToken`. Therefore Ant keeps `network_isolation = false` for all executors today; `network-isolation-unavailable` remains a live blocker; cache lookup/store/reuse stay unwired per D-003 (superseded 2026-11-13 by the T2.8 addendum: mechanics are now wired behind the blocker gate, which this decision's outcome keeps closed); and policy-only controls (hosts/proxy/env) are rejected as dishonest for cache gating. The dedicated-sandbox-user approach (elevated `ant sandbox setup`, DPAPI-protected credentials, idempotent read-back-verified rules, `LocalPolicyModifyState` fail-closed validation, per-machine network granularity with per-workspace filesystem granularity) is documented as the future implementation slice; AppContainer remains an opt-in future mode and `Experimental_CreateProcessInSandbox` is re-evaluated before M4. **Addendum (2026-11-13):** the dedicated-sandbox-account path is implemented as D-013; `network_isolation` is true only for that executor.

### D-010: Adapter contract is in-process; Cargo is the first adapter; generated actions stay non-cacheable
**Status:** Adopted 2026-11-13 (updated T3.4). The adapter contract (`build-adapter`, T3.1) is an in-process trait — `detect` + `generate` producing the canonical `build-graph::PlanFile` — wired into `ant adapt`; an external adapter protocol can be added later without breaking this contract because adapters emit the same plan-file format the run path loads. Two ecosystems are landed, each chosen on the research-required feasibility ground (T0.4: "choose based on actual user demand and feasibility; the spec's candidate list is not itself priority evidence"): **Cargo** (T3.2: `cargo metadata` is a stable offline-friendly JSON API and real adapt → run → artifact verification is possible) and **npm** (T3.4: `node`/`npm` are present in the development environment, so real adapt → run → artifact verification against a TypeScript project is possible; feasibility probed before implementing — cmake/make/msbuild were absent). Generated actions use `cache_policy: never` by construction: where dependency content cannot be declared as an input — cargo registry sources live outside the workspace; the installed npm `node_modules` tree is derived, not source — under-declared inputs must never claim cache eligibility (D-003 spirit). Toolchain identity is captured truthfully from the resolved executable (cargo for cargo; `node` for npm, because `npm` is a script, not an executable). The npm adapter declares no outputs in v1 (npm has no standard layout — unknown layouts are omitted, not guessed, per the honesty rule) and handles the Windows `npm.cmd` batch-shim spawn issue via `cmd /C npm run build`. **T3.5 addendum:** without `--adapter`, `ant adapt` selects an adapter only when exactly one detects the project; no ecosystem priority is invented (ambiguity fails asking for `--adapter`), and detection errors fail closed. Honest v1 limitations (cargo default `target` layout; npm no declared outputs; npm monorepos unsupported; full dependency resolution required; platform-native path separators) are documented in `docs/cli/adapters.md`. **Batch C addendum (T3.6–T3.11):** adapters accept adapter-defined `--option KEY=VALUE` settings validated before any side effect (the one shared-contract change: `generate` takes `&AdapterOptions`; the plan-file format is unchanged); cargo maps the `release` profile and in-project target directories (outside fails closed; non-default dirs are pinned via `CARGO_TARGET_DIR` because the child environment is cleared) and declares in-project dependency sources (vendored crates, non-member path deps) plus `.cargo/config.toml`, which makes `cargo vendor` the verified hermetic path for registry dependencies under `--sandbox`; npm generates one action per workspace package with a build script and declares outputs only on the user's explicit `outputs=entry-points` assertion, because no `package.json` field states what a build produces; a third adapter, CMake, was added on the same feasibility ground (VS-bundled CMake + MSBuild verified adapt → run → artifact; not sandbox-compatible with the VS generator). Every generated action remains `cache_policy: never`.

At each milestone, update its state, list changed files, validation results, unresolved questions, and next independently actionable task. A successor should be able to take the first `Not started` task without reinterpreting the full master specification.
