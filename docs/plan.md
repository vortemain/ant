## Product roadmap (2026-11-13, decision D-016 — read `docs/vision.md` first)

The owner's vision is a Bun/Expo-class tool that covers **everything**: every platform and language, few commands, very fast, **local-first** (D-026: most developers build on their own laptop; servers are an optional extension), with a polished dashboard. The phases below order that work by dependency; each phase ends in something a developer can use. The M-milestone table that follows remains the engineering record of what exists; this roadmap decides what comes next.

| Phase | Outcome a developer gets | Builds on | Exit criteria |
|---|---|---|---|
| P1 Front door | `ant init` / `ant build` with zero required configuration: detect the project, pick the adapter, build, package into `dist/`, reuse what is provably reusable; a minimal `ant.toml` only when needed; plumbing commands stay for power users | adapters, plans, local executor, cache | a Rust, an npm, and a CMake project each build with `ant build` alone; clear errors; docs show only the short commands — **met on Windows (2026-11-13, P1.1)**; deliverables are collected for Rust only so far (npm/CMake outputs stay where their tools write them); the Linux build and full test suite pass in CI since P2.1, but `ant build` has not yet been exercised on Linux by hand |

## Decision log

### D-001: Start with contracts and one Rust workspace
**Status:** Adopted provisionally. Cargo workspaces support shared metadata and commands; crate boundaries should follow stable responsibilities. Source: [Cargo workspace reference](https://doc.rust-lang.org/cargo/reference/workspaces.html). Keep the initial member count small. Revisit after first vertical slice.

### D-002: Treat REAPI as an interoperability target, not the internal domain model
**Status:** Adopted provisionally. The upstream project describes a set of APIs for input upload, execution, monitoring, and content-addressed caching. Mapping at the remote boundary keeps local semantics independent. Source: [Bazel Remote APIs repository](https://github.com/bazelbuild/remote-apis). Exact feature/conformance scope remains open.

### D-003: Default actions to non-cacheable
**Status:** Adopted. Correctness and secret isolation require conservative behavior when declared inputs or hermeticity are incomplete. **Addendum (2026-11-13, T2.8):** the letter changes from "unwired in the run path" to "wired behind the blocker gate" — `ant run --plan --cache-dir` now computes the action-key candidate from pre-run digests and stores/looks up only when the candidate reported no blockers. The gate's spirit is unchanged and stronger-tested: every executor still reports `network-isolation-unavailable` (D-009), so `cache_eligible` is false for every real key and nothing is reused; an end-to-end test proves a fully-declared action writes no cache entries. Cache failures degrade to misses/warnings, never to trusting unverified content. **Addendum (2026-11-13, T2.10):** the gate now opens for exactly one executor, `--network-isolated` (D-013); reuse is proven end to end there and remains impossible under every other executor.

### D-055: `server` in ant.toml is a preference; `--on` is an order
**Status:** Adopted 2026-11-16 (P8.5). A team commits `server = "NAME"` to `ant.toml`, but its members differ: some are on another OS, some are offline, some run a signed release. When the server came from `ant.toml`, any reason it cannot take this build (unknown server, other OS, missing OS record, signed release, the SSH tunnel failing) is printed ("Building on this machine: NAME (server in ant.toml) cannot take this build: …") and the build runs locally. `ant build --on NAME` still fails with that reason, and `--local` skips the server silently. The connection is made before planning, so a fallback costs one failed SSH attempt. Verified by `front_door.rs` (fallback with the reason, `--on` refusing, `--local`). Not yet: choosing by load or measured speed.

### D-054: A failed remote action cancels the others
**Status:** Adopted 2026-11-16 (P8.5). With actions running in parallel (D-050), a failure used to let the rest finish for nothing. The client now cancels every job still in flight (`POST /v1/jobs/{id}/cancel`, client role) and reports them `status=cancelled`. The coordinator fails a queued job at once ("cancelled before it started") and flags a running one; the worker's output flusher now posts every 250 ms even without output (a heartbeat) and the coordinator answers `{"cancel": true}` for a flagged job, so the worker cancels the executor's token and the tool is killed (with its process tree on Windows). Older workers ignore the answer and finish the job, which is harmless. The same change gives sandboxed Linux workers live output: the bubblewrap executor now tees stdout/stderr through `OutputCapture` like the direct one (D-049). Verified by `a_failure_cancels_the_other_remote_jobs` (two real workers: a failing action, a running and a queued 30 s action; the client returns in about 5 s and both slow jobs end without succeeding) and the existing output tests; the Linux sandbox path compiles for Linux here and runs in CI. Not yet: cancelling from the dashboard, and output from the Windows restricted-token sandbox.

### D-053: Servers in the dashboard
**Status:** Adopted 2026-11-16 (P7.5). The dashboard gains a Servers page listing the profiles `ant server deploy` saved (name, SSH target, OS and architecture, when deployed; never tokens) from `GET api/servers`, with a "Check now" button per server calling `GET api/servers/<name>/status`, which opens the SSH tunnel and reports the coordinator's version and online workers, or the error. Because the dashboard answers requests one at a time, the status check runs on its own thread with the connection moved to it. Neither route changes anything, so they need no `X-Ant-Dashboard` header (D-046). Folder deliverables (D-051) show as folders with their total size instead of "No longer on disk", and .NET gets a badge. Verified in the browser against real local history and a profile with no token (the error shows), and with the accessibility audit (no issues, light and dark, Servers and Deliverables). Not yet: deploy or remove servers from the dashboard, worker detail, team access.

### D-052: Secrets in the system keyring on macOS and Linux
**Status:** Adopted 2026-11-16 (P4.5). Signing passwords (D-033) and server tokens (D-047) were sealed with DPAPI on Windows but stored as 0600 files elsewhere. On macOS they now go to the Keychain (`security -i`, the command and secret on stdin, read back to confirm because `security -i` exits 0 on errors) and on Linux to the Secret Service (`secret-tool store`, the secret on stdin), hex-encoded, under a random id; the file keeps only `ant-keyring:v1:<id>`. Secrets never appear on a command line. Where no keyring answers (a headless server), Ant keeps the 0600 file and says so (`ant signing status`, the key-creation message); secrets stored before this change keep working. `ant server forget` also deletes the keyring entry. Verified by `verify-keyring.yml`: a real unlocked Keychain on macOS and gnome-keyring over D-Bus on Linux, with `ANT_REQUIRE_KEYRING=1` forbidding the fallback (the blob must be a reference, must not contain the secret, must round-trip, and must be gone after forgetting). Not yet: KWallet without Secret Service, and moving secrets stored before this change into the keyring.

### D-051: Real builds per ecosystem; folders as deliverables; .NET
**Status:** Adopted 2026-11-16 (P6.3/P5.1). The P6 adapters had been unit-tested but never built real projects. Small real projects now live in `examples/` and `scripts/verify-adapters.sh` builds each with `ant build` (twice) and runs what lands in `dist/`; `verify-adapters.yml` runs Maven, Python, Docker, .NET, and Flutter on Linux, Maven, Python, and .NET on Windows, and the iOS app on macOS. Doing so found and fixed: Maven collected nothing (now the packaged archives); setuptools' `src/*.egg-info`, written during the build, failed every src-layout Python build as "input changed while the action ran" (now `src/` is declared entry by entry without it); Flutter web delivered and reused only `index.html` and `main.dart.js`, which do not run (now `build/web/` is a tree output, collected whole into `dist/web/`); Xcode omitted `-scheme` (xcodebuild refuses `-derivedDataPath` without one), used `-project` for workspaces, missed sources outside `Sources/` and `App/` (so an edit could be wrongly reused), and collected no `.app`. `ant build` now collects directory deliverables (copied, symlinks skipped; stale ones removed). New `dotnet` adapter (`dotnet publish` into `.ant/dotnet/<name>`, collected into `dist/<name>/`, `cache_policy: local`). Verified on this Windows laptop for Maven (the JAR runs), Python (the wheel installs and imports), and Flutter (the web app from `dist/web/` renders in a browser with no console errors; a no-change rebuild restores it in 2.4 s vs 41 s), and in CI as above. Not yet: Docker on Windows runners, Flutter mobile targets, signed iOS (needs the owner's Apple identity).

### D-050: Several workers per server; independent actions build in parallel
**Status:** Adopted 2026-11-16 (P8.4). The remote client (`ant build --on`, `ant remote run`) used to run a plan's actions one after another. It now submits every action whose dependencies have finished, keeps polling all submitted jobs, and submits more as they complete; the coordinator's queue and the workers' one-job-at-a-time leases do the placement, so with N workers up to N independent actions build at once. Fail-fast is kept: after a failure nothing new is submitted, already-submitted jobs finish, and the rest are reported skipped. With more than one action, each line of streamed output (D-049) is prefixed with its action id so interleaved output stays readable. `ant server deploy --workers N` (1-16, default 1) runs the original `ant-worker` service plus a systemd template `ant-worker@2..N`, each with its own work directory (`/var/lib/ant/worker-N`) and id (`<host>-N`); redeploying with fewer workers disables the extra ones. The same change fixes a D-048 flaw: kept workspaces recorded one input list per project, so syncing one action deleted another action's inputs, which the next job had to re-send with fresh modification times; now the record of what is on disk is shared per project and each action has its own list of inputs it may remove. Verified: e2e tests with two real workers (two independent 3 s actions overlap, run on different workers, a dependent action sees both outputs, output lines carry action ids) and a kept workspace where a second action still finds the first one's input; `server-deploy.yml` deploys four workers on a real Linux host, checks "4 workers online", runs four CPU-bound actions with four workers and again after a redeploy to one worker, and requires a speedup over 1.5x; measured on a 4-core GitHub runner (run 43811355320): 6.38 s with one worker, 2.76 s with four, **2.31x**. Kept workspaces live per worker, so the coordinator remembers which worker last ran each project's action (`<workspace key>/<action id>`) and holds that job for it up to 5 s while it is alive (polled in the last 10 s); otherwise any worker takes it. Verified by a coordinator unit test and in `server-deploy.yml`, where an offloaded rebuild with four workers lands on the same worker as the first build. Not yet: cancellation of submitted jobs after a failure, several servers in one build, load-aware placement.

### D-049: Live tool output from remote jobs
**Status:** Adopted 2026-11-16 (P8.3). An offloaded build (`ant build --on`, D-048) and `ant remote run` now show the tool's own output live, as a local build does. Workers tee the direct executor's output (the same `OutputCapture` as D-045) into a per-job buffer and send it every 250 ms to the coordinator (`POST /v1/jobs/{id}/log`, worker holding the running job's lease only; trailing partial UTF-8 characters are held back), then flush once more before posting the result. The coordinator keeps up to 4 MiB per job in memory (then marks it truncated); clients and viewers read it from a byte offset (`GET /v1/jobs/{id}/log?from=N`). `ant build --on` writes it to the terminal's stderr and into the build's dashboard log; `ant remote run` writes it to stderr and keeps stdout for its machine-readable lines. A client talking to an older coordinator stops asking and builds anyway. No secrets are involved: offloaded builds never carry them (D-048). Verified: an e2e test streams two lines (stdout then, a second later, stderr) through real coordinator and worker processes and sees them in order and in more than one piece, and checks that clients and other workers cannot write a job's output, viewers can read it, and bad offsets are refused; `server-deploy.yml` checks that cargo's own `Compiling` line reaches the developer's terminal from the real server. Not yet: output from sandboxed workers, colors (the worker's tool output is a pipe), output kept past a coordinator restart.

### D-048: `ant build --on SERVER`: offload to your own server, incrementally
**Status:** Adopted 2026-11-15 (P8.2). `ant build --on NAME`, or `server = "NAME"` in `ant.toml` (with `ant build --local` to build here anyway), runs the build on a server set up with `ant server deploy` and collects deliverables into `dist/` exactly like a local build, recorded in history as "on NAME". The plan is still made on the developer's machine, so offload requires the **same OS** on both sides (recorded from `uname` at deploy time; older profiles ask for one redeploy) and the local toolchain to plan with; a different CPU architecture only prints a note. **Signed releases are refused**: signing secrets never leave the machine (D-033). Jobs carry an optional `workspace_key` (protocol field, ignored by older workers' absent-field default; 16-64 lowercase hex, here 32 characters of a digest of the project's path): a non-caching worker then keeps one workspace per project under `<work-dir>/projects/<key>` (the 8 most recently used are kept), syncs only changed inputs with fresh modification times, deletes inputs that disappeared, and never touches files that were not inputs, so cargo's `target/` and Gradle's `build/` survive and remote edit loops are incremental. Kept workspaces are never used by cache-producing (sandboxed) workers: shared results still come only from fresh, isolated workspaces (D-019). An invalid key fails the job. `ant server deploy --toolchain rust` installs Rust (rustup, minimal profile) for the `ant` service account, and a C linker when missing; the worker service's `PATH` includes it. Verified in `server-deploy.yml` on a real Linux host: an offloaded `cargo new` project builds there as `ant` with the server's own toolchain, its binary lands in `dist/` and runs, the kept workspace holds `target/`, and an edit rebuilds with the new code; locally the refusals (unknown server, other OS, missing OS, `--on` with `--local`, `ant.toml` `server`) are tested in `front_door.rs`, and kept workspaces (state survives, edits arrive, no key means fresh, bad keys refused) in `remote.rs`. Not yet: streaming the tool's own output during an offloaded build, automatic choice between local and server, other toolchains (`--toolchain` accepts only `rust`; others must be on the `ant` user's PATH), and cross-OS offload.

### D-047: `ant server deploy`: your own Linux server over SSH, no open ports
**Status:** Adopted 2026-11-15 (P8.1). `ant server deploy USER@HOST [--name] [--port] [--identity] [--binary PATH] [--sandbox]` turns a Linux server into an Ant build server with one command. It drives the system `ssh`/`scp` with `BatchMode=yes` (keys or agent only; Ant never handles a password) and `StrictHostKeyChecking=accept-new` (first contact is remembered; a changed host key still stops it); targets that look like ssh options or carry shell metacharacters are refused. It checks the host (Linux, systemd, root or passwordless `sudo -n`, CPU architecture), then runs one idempotent setup script as root: install `/usr/local/bin/ant` (an uploaded `--binary`, or the matching musl build from the latest GitHub Release downloaded on the server; either way verified against SHA-256 and test-run before it replaces the old one), create a system `ant` user, `/etc/ant` (`750 root:ant`) with client and worker tokens generated on the server from `/dev/urandom` (`640 root:ant`, kept across redeploys), `/var/lib/ant`, and two hardened systemd services (`User=ant`, `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, writes only to `/var/lib/ant`): the coordinator on the server's **own loopback** `127.0.0.1:8742` and one worker (optionally `--sandbox`). Nothing is exposed to the network: Ant reaches the coordinator through an SSH tunnel it opens per command (`ExitOnForwardFailure`, a free local port), so no TLS certificate, reverse proxy, or firewall change is needed. The client token is read back once over SSH and stored with the signing passwords' sealing (DPAPI on Windows, 0600 elsewhere) next to a non-secret profile in the per-user data directory. `ant server status|list|forget` and `ant remote run --server NAME` use the profile. Verified by `.github/workflows/server-deploy.yml` on a GitHub Ubuntu runner acting as the server with a real sshd: deploy (upload, verify, services active, worker registered), `status` through the tunnel ("1 worker online"), a real build on the server through `ant remote run --server` (output came back, ran as the `ant` user), an idempotent redeploy with the client token unchanged, the coordinator unreachable on the server's network address, and the token and directory permissions exact. Not yet: deploying *from* Windows or macOS (the client path is the system ssh there too, untested), offloading `ant build` automatically, several workers or servers per build, TLS for teams that want a public endpoint (the documented Caddy setup still applies), and removal from the server (`forget` prints the command).

### D-045: Live build output: tee through pipes, keep the terminal's look
**Status:** Adopted 2026-11-15 (P7.3; supersedes D-044's "not adopted yet" for live logs). D-044 deferred output capture because a pipe makes tools drop colors and progress bars. Instead of a pseudo-terminal (a large new FFI and spawn path), `ant build` now tees: the direct local executor accepts an optional `OutputCapture` on `PreparedAction` (like secrets, never part of the action, key, or plan), spawns the tools with piped stdout/stderr, and two pump threads forward every chunk unchanged to Ant's own stdout/stderr and into a sink. Tools keep their look through *display-only* spawn variables: when Ant's stderr is a real terminal and the project is cargo (or Tauri), `CARGO_TERM_COLOR=always` plus `CARGO_TERM_PROGRESS_WHEN=always` and `CARGO_TERM_PROGRESS_WIDTH` = the console's width (new audited `ant-sandbox-win::console::stderr_width`; `COLUMNS` elsewhere). Other tools print as they would to a pipe (Gradle already runs with `--console=plain`). After the child exits the executor waits at most 2 s for the pumps (a daemon the action left running can hold the pipe open), then moves on. Plumbing commands (`ant run`, workers) are unchanged: no capture, inherited terminal. **Logs:** `<user cache>/history/logs/<build id>.log`, line-buffered so every injected secret value (D-033) is replaced with `****` even when split across reads, capped at 5 MB with a note, newest 100 kept. **Dashboard:** `GET api/log/<id>?from=N` returns up to 256 KB from offset N (never cutting a UTF-8 character) with the next offset and current size; running builds offer "Show live output" (refreshed every second), finished builds "Show output" in their expanded row; a dark terminal-style panel renders ANSI colors as CSS classes (text nodes only), drops other escape sequences, collapses `\r` progress redraws to their final state, follows the end only when already scrolled there, and keeps the last 5,000 lines; every color is at least 4.5:1 on the panel, dimmed included. Verified on Windows with a real 21 s cargo build started in a real terminal: the terminal showed cargo's normal colored output and progress bar (the log holds the bar's `\r` redraws, `Building [====> ] 113/114`), the dashboard streamed the output live in color while it ran, and afterwards the expanded row showed the clean ten-line output ending in "Finished"; unit tests cover the executor tee (both streams, display variables not in the action), secret masking across chunk boundaries, the size cap, offsets, id sanitizing, UTF-8-safe chunks, and the log API. Not yet: colors for non-cargo tools in the terminal (they print plain once piped), a true pseudo-terminal for tools that need one.

### D-043: Distribution: GitHub Releases, one-line installers, `ant upgrade`
**Status:** Adopted 2026-11-15 (owner: "the usable way to install", not necessarily npm or pip). Ant ships as one self-contained executable per platform; no runtime, no package manager required. **Release workflow** (`.github/workflows/release.yml`): on a pushed `v*` tag (or manually, or on pushes to `release-dry-run`) it builds `x86_64`/`aarch64` Windows (MSVC), macOS, and Linux (musl, fully static), smoke-runs the native ones, writes `VERSION` (checked against the tag) and `SHA256SUMS`, tests both installers and `ant upgrade` against the fresh files on Linux, Windows, and macOS through a loopback mirror, and only for a tag publishes a GitHub Release. Asset names are the contract: `ant-<target>[.exe]`, `SHA256SUMS`, `VERSION`, read through GitHub's stable `releases/latest/download/<asset>` (or `releases/download/v<version>/<asset>`) addresses, so nothing needs the GitHub API or an unzip step. **Installers** (`scripts/install/install.ps1`, `install.sh`, served from the repository's raw URLs until there is a domain): detect OS and CPU (Rosetta shells get the Apple Silicon build), download with `Invoke-WebRequest`/`curl`/`wget`, verify SHA-256 and refuse to install on mismatch, install without admin rights to `%LOCALAPPDATA%\Ant\bin` or `~/.ant/bin`, and add it to the user PATH (shell profiles, fish); `ANT_VERSION`, `ANT_INSTALL_DIR`, `ANT_NO_MODIFY_PATH`, `ANT_DOWNLOAD_BASE` adjust them. The PowerShell installer runs in a child scope so `irm | iex` leaves the session untouched, and renames a running `ant.exe` aside. **`ant upgrade [--check] [--version X]`**: reads `VERSION`, compares numerically, downloads this platform's binary, verifies it with plain SHA-256 (not Ant's domain-separated content digest, which the first local test showed can never match `sha256sum`), swaps it in (on Windows the running `.exe` becomes `ant.exe.old`, replaced by the next upgrade; on failure the old binary is put back), and runs the new one; HTTPS only, except plain HTTP to a loopback mirror. Dependencies: `ureq` (already used by `ant-remote`) and `sha2` (already in the workspace) become direct `ant-cli` dependencies; nothing new enters the tree. Verified on Windows: the PowerShell installer piped to `Invoke-Expression` against a loopback mirror installs a working `ant`, leaves no variables or preferences in the session, refuses a tampered `SHA256SUMS` and installs nothing; `ant upgrade` reports, upgrades (running-executable swap), pins a version, refuses a tampered checksum without touching the binary, and refuses a plain-HTTP non-loopback base; `crates/ant-cli/tests/upgrade.rs` runs check/tamper/swap/missing-release on every CI platform. **Not yet / owner decisions:** no release is published (that needs a version tag); a license (package managers and companies require one); the `ant` command name collides with Apache Ant; Windows Authenticode and macOS notarization (SmartScreen and Gatekeeper warn on unsigned downloads); winget, Scoop, and Homebrew manifests once releases exist.

### D-033: Signed Android releases; secrets are injected at spawn, never declared
**Status:** Adopted 2026-11-14 (P4.3). `ant build --release` (or `ant build android --release`) in an Android project runs `assembleRelease bundleRelease` and collects the signed `<module>-release.apk` and `.aab` into `dist/`; plain `ant build` stays a debug build (installable with no setup). On first release Ant generates the project's upload key with the JDK's `keytool` (RSA 4096, PKCS#12, alias `upload`, random 48-hex-character password from the OS CSPRNG, passed to `keytool` through its environment, never argv). `ant signing import` brings an existing key (passwords read from `ANT_SIGNING_STORE_PASSWORD`/`ANT_SIGNING_KEY_PASSWORD`, so Ant never prompts or echoes them); `ant signing status` shows the certificate fingerprint and where and how the key is stored; `ant signing export --out DIR` writes the explicit backup (keystore + `signing.txt` with the passwords; refuses to overwrite). Keys live per application id in the per-user **data** directory (`%APPDATA%\Ant`, `~/Library/Application Support/Ant`, `$XDG_DATA_HOME/ant`; `ANT_DATA_HOME` overrides), never in the cache directory or the project. On Windows passwords are sealed with DPAPI for the current user (new audited FFI in `ant-sandbox-win::secrets`, with `BCryptGenRandom`). **Accepted gap:** elsewhere they are 0600 files, not yet encrypted at rest (macOS Keychain / Secret Service integration is open); `ant signing status` says which applies. **Secret contract (first real use of the architecture's "secrets are references injected by a trusted executor"):** `local_executor::SecretEnvironment` travels on `PreparedAction`, not on `Action`, so secrets never reach plan files, action keys, cache entries, events, or logs; its `Debug` prints names only and values are overwritten on drop; only the direct local executor injects them, and every sandboxed or network-isolated path fails closed on a prepared action that carries any. The front door passes the Android Gradle Plugin's `android.injected.signing.*` properties as `ORG_GRADLE_PROJECT_*` environment (Gradle reads those as project properties), so no build-file change is needed. Only the certificate's public SHA-256 fingerprint becomes key material (`ANT_ANDROID_SIGNING_CERT_SHA256` in the action environment), so a release signed with one key is never reused for another. Verified on Windows with the minimal Android app: `apksigner` and `jarsigner` verify the outputs against the generated certificate; the 48-character password does not appear in `.ant/`, the plan, Ant's caches, the key folder, the project's `build/` and `.gradle/`, Gradle's daemon logs, or Gradle's caches; an unchanged release is reused in 0.9 s, a different key rebuilds and signs with the new certificate, and switching back restores the release signed with the first key.

### D-032: Local Android builds use the developer's homes and a warm Gradle daemon
**Status:** Adopted 2026-11-14 (P3 next actions 4 and 5). Verified locally on Windows with a minimal plain-Java Android app (AGP 8.11.0, Gradle 8.14.3, compileSdk 35): before this, Gradle plans redirected `GRADLE_USER_HOME`/`ANDROID_USER_HOME` into `.ant/` (a first local build would re-download AGP and every dependency, and each project got its own debug key) and always passed `--no-daemon` (a one-line edit took 37–88 s against 6–30 s for Gradle with a warm daemon). Now: (1) the Gradle adapter has `home=project|user`; `ant build` passes `user`, which declares the developer's `~/.gradle`, `~/.android`, `JAVA_HOME`, and the Android SDK (env, else `local.properties`, else the default install location) as absolute action environment, because the child environment never inherits profile variables. These values are key material, so such results stay machine-local. `project` stays the default for `ant adapt`, sandboxed runs, and workers. (2) A new optional action field `background_services` (default false, omitted when false, excluded from the key like `resources`) lets helper processes outlive the action: on Windows the unsandboxed executor adds `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` to the action's kill-on-close job, so processes the action starts leave the job; sandboxed, network-isolated, and memory-capped runs ignore the flag. **Accepted risk:** for such actions, cancellation and timeouts stop the main process but not the helpers it started (a cancelled Gradle client may finish its build in the background). `home=user` plans set the flag and drop `--no-daemon`. (3) Gradle opts into the plan cache (JDK on `PATH`, `JAVA_*`/`ANDROID_*`/`GRADLE_*`/home environment, default SDK locations). Measured (hand-run, `benchmarks/local/results/2026-11-14-windows-android/`): one-line edit 2.3–4.4 s (was 37–88 s; Gradle with warm daemon 6.2–29.5 s); switch back to built code 0.3–0.9 s (Gradle 6.9–10.0 s); no change 0.11–0.35 s (Gradle 5.9–8.6 s); the APK in `dist/` verifies with `apksigner` and carries the standard Android Debug certificate. Ant also found the SDK with no configuration where plain `gradlew` failed ("SDK location not found"). One unexplained Gradle plan-cache miss was observed once and not reproduced in 14 further runs (a miss only regenerates the plan).

### D-031: Local result keys stay path-specific for cargo (P3 next action 2, decided)
**Status:** Adopted 2026-11-14. The proposal was to drop the workspace path from local keys so a second clone or worktree of the same repository restores instead of rebuilding. Not adopted for cargo, because cargo builds embed absolute paths in ways that change behavior, not just bytes: `env!("CARGO_MANIFEST_DIR")` expands at compile time to the package's absolute directory (code that locates assets or fixtures through it would, in a restored binary, read the *other* clone's files), and debug info plus the PDB path embedded in Windows executables point at the clone that built them. Remapping paths (`--remap-path-prefix` through `RUSTFLAGS`) would make outputs relocatable but changes cargo's own fingerprints, so a developer alternating `cargo build` and `ant build` would rebuild everything each time. Path-independent sharing stays available where it can be proven: sandboxed Linux workers build under the fixed mount `/tmp/ant/ws` (D-019). Revisit per adapter: Gradle's own build cache treats paths relatively, so Gradle results may become relocatable once Android builds run through `ant build` and that can be verified.

### D-030: Restores hard-link from the local results store
**Status:** Adopted 2026-11-14 (P3 next action 1). Measured on this repository (Windows, debug): restoring ~70 MB of outputs took 1.3–1.6 s (copy + re-digest) of a 2.7 s switch-back. Now `build-cache` restores by hard link when the store and the workspace share a volume (copy fallback, re-digested), only for `ant build`'s local reuse and only while change detection is on; sandboxed and network-isolated runs keep private copies. Integrity checks stay, but cost a stat instead of a read: each blob is verified against its digest through the change-detection cache keyed on the blob directory (re-read whenever its size, mtime, or change marker moved), and the restored file's digest is recorded so it is not re-read either. Stores still copy, because cargo's uplifted outputs are already hard links into `target/<profile>/deps` and a linker writing in place there must never reach the store. Before an action re-executes, `Cache::break_links` gives each still-linked declared output a private copy, so tools that rewrite outputs in place (found by the network-isolated cache test: `copy /Y` onto a linked output failed, since a link shares the blob's ACL) never write into the store. Anything outside Ant that rewrites a linked output in place changes the blob's stamp; the next restore re-digests it, finds the mismatch, deletes the blob, and reports a miss. `Cache::store` now rewrites an entry whose blobs are missing, so a dropped blob does not turn its key into a permanent miss. Result: restore 1.3–1.6 s → ≈0.014 s once blobs are verified.

### D-029: `ant build` caches plans, keyed on what shapes them
**Status:** Adopted 2026-11-14 (P3 next action 3). Plan generation was ≈0.4–0.5 s of every cargo `ant build` (`cargo --version` + `cargo metadata` through the rustup proxy; Windows process start dominates), more than cargo's whole no-change build. D-027 had kept plans uncached because a rustup toolchain switch does not change the proxy's file stamp. Now adapters may opt in with `BuildAdapter::plan_cache_probe`, a subprocess-free list of key material covering everything *outside the project* that can change the plan. Cargo's probe: `PATH` and every `CARGO*`/`RUSTUP*`/`RUST*` variable; the stamps of the cargo proxy and the binary it resolves to; rustup's `settings.toml` (default toolchain and overrides) and every installed toolchain's `cargo`/`rustc`; the user's cargo `config(.toml)`; and `.cargo/config(.toml)` and `rust-toolchain(.toml)` in every ancestor directory. The front door adds the adapter name, its options, Ant's version, the project's top-level listing (minus `.ant`, `.git`, the output directory, and the top-level directories of declared outputs), and the content digest of every input the cached plan declares, read through change detection. The cache keeps the 8 most recent plans per workspace in the per-user cache directory (switching branches back and forth keeps hitting). `--fresh` bypasses it, read/parse failures are misses, and a hit recreates the scratch directories generation would have made. `--verbose` prints `plan=reused-from-cache`. Trust model: same as D-027/D-028. Verified: a `RUSTUP*` variable change, a new top-level file, and a manifest edit each regenerate; switching back hits (e2e test). Only cargo opts in so far.

### D-028: `ant build` reuses this machine's own results (local trust, like Turborepo)
**Status:** Adopted 2026-11-13 (owner chose "Yes, like Turborepo"). Proof-based reuse (sandbox + network isolation) stays the only way results are *shared*; on top of it, plain `ant build` now reuses results **built on the same machine** without a sandbox. A new plan policy `cache_policy: local` means every output-affecting input is declared or pinned but some pinned content lives outside the project: cargo plans with a `Cargo.lock` whose non-member packages are registry/git (lock-pinned) or inside the project (path dependencies outside the project stay `never`), and Gradle plans without in-project dependencies. Keys use content-only digests (a branch switch or re-checkout that rewrites timestamps still hits) and the normal key material (argv, env, toolchain identity, platform, workspace path), then are domain-separated (`build_digest::trusted_local_key`): only the blockers no-sandbox, no-network-isolation, content-only digests, and local-only policy are accepted; `never` policy, a missing toolchain identity, or input-digest mismatches still block. Results go to a separate per-user store (`<user cache>/local-results`) that is never uploaded or shared. Actions without declared outputs (npm by default, CMake) are not reused. `ant build --fresh` skips lookups (and refreshes the stored result). Restores skip outputs already in place with the right content (checked through the change-detection cache). **Accepted risk:** a build that reads an undeclared, unpinned input could be reused stale on this machine; `--fresh` is the escape hatch. Measured on this repository (Windows, debug): switching back to previously built code 2.7–4.5 s vs cargo 10.0–11.0 s; nothing changed 0.55 s vs cargo 0.45 s.

### D-027: Change detection, absolute temp dirs, and one cargo invocation for `ant build`
**Status:** Adopted 2026-11-13 (P3.1). (1) Developer commands (`ant build`, `ant run`, `ant remote run`) keep a per-workspace change-detection cache in the per-user cache directory (never in the workspace, so it can never become an input): a file's digest is reused while its size, modification time, and change marker (inode+ctime on Unix, creation time on Windows) are unchanged and the entry was recorded at least 2 s after the modification (git's racily-clean guard). Workers never enable it. `ANT_NO_DIGEST_CACHE=1` turns it off. Trust model: same as make/git. (2) Plans keep declaring `TMP`/`TEMP`/`TMPDIR` workspace-relative (path-independent keys), but executors make relative values absolute against the action's working directory at spawn time: cargo build scripts run in other directories and the MSVC linker failed with LNK1104 under `ant build` on Windows (a pre-existing bug found by running `ant build` on this repository). (3) `ant build` asks the cargo adapter for `granularity=workspace` by default: one `cargo build --workspace` instead of one invocation per member (cargo parallelizes crates itself; a no-change build paid cargo's startup per member). Measured on this repository (Windows, debug, nothing changed): `ant build` 4.8 s → 2.9 s (change detection) → 1.2 s (one invocation); plain `cargo build` 0.45 s; the rest is plan generation (`cargo metadata` + `cargo --version`, ≈0.5 s), deliberately not cached because a rustup toolchain switch does not change the cargo shim's file stamp.

### D-025: Gradle's task cache is served by the coordinator, written only by workers
**Status:** Adopted 2026-11-13 (P4.2). On an Ant cache miss the worker starts from an empty workspace, so every edit was a full Gradle build. Workers started with `ant worker --sandbox --task-cache` (Linux only) now serve Gradle's HTTP build cache to actions declaring `ANT_GRADLE_TASK_CACHE=1` (the Gradle adapter does so for cache-eligible plans, with `--build-cache`): a host-side Unix socket per job forwards `GET`/`PUT /cache/{key}` to `/v1/task-cache/gradle/{key}` with the worker's token; the socket's directory is bound into the sandbox, where `ant __gradle-cache-bridge` listens on the sandbox loopback, writes an init script into `$GRADLE_USER_HOME/init.d`, and runs the action. The token never enters the sandbox and the sandbox gains no other network. Clients and viewers cannot write entries. **Trust:** any build that runs on a worker can write any Gradle key, so the task cache trusts every project the workers build: right for one owner's servers, not for a multi-tenant service (would need per-tenant namespaces). Cache-eligible Gradle plans no longer pass `--offline` because Gradle disables its remote cache in offline mode; the no-network sandbox still fails a missing dependency. Measured on JetNews (run 43474904549): one-file edit 72.6–74.2 s (18/36 tasks from cache) vs ≈150 s before; Gradle's warm incremental edit is 2.0–3.3 s.

### D-024: Gradle/Android builds are cacheable only with in-project dependencies
**Status:** Adopted 2026-11-13 (P4.1). The `gradle` adapter runs one wrapper task per project with the whole project (minus `build/`, `.gradle/`, IDE and Ant dirs) as input and each application module's debug APK as output. Gradle fetches dependencies and its distribution from the network, so the action is cache-eligible only when both are project inputs: `.gradle-deps/` (a read-only copy of `caches/modules-2`, passed as `GRADLE_RO_DEP_CACHE`) and a local `distributionUrl`; it then runs `--offline`, Kotlin in-process, with Gradle's and Android's homes inside the workspace. `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT` join the Unix environment allowlist as key material; the JDK and SDK themselves are not digested (accepted gap, documented). Measured on JetNews (run 43465528849): cold 159 s vs Gradle 157 s; unchanged/fresh checkouts 0.65–0.86 s vs Gradle (warm daemon + build cache) 1.6–4.6 s.

### D-023: Blobs move in verified batches
**Status:** Adopted 2026-11-13 (P2.6). Cold remote builds of Ant itself cost ~255 s against ~30 s for cargo because 6,430 files moved one HTTP request each. `POST /v1/blobs/batch-put` and `batch-get` carry many blobs per request in a length-prefixed framing (≤ 1024 blobs, senders split at ~32 MiB) without weakening any guarantee: every blob is re-hashed, one bad blob rejects a whole upload batch with nothing stored, downloads never return partial sets, viewers are refused. Measured: cold 33.3 s vs cargo 24.3 s in the same run (transfer overhead ~225 s → ~7 s). Single-blob routes stay for small transfers and compatibility.

### D-022: Remote cache keys are computed before inputs are downloaded; files carry the executable bit
**Status:** Adopted 2026-11-13 (P2.5). The first full benchmark showed cache hits on Ant itself costing ~216 s because the worker materialized all inputs before consulting the cache. The worker now derives the key from the job's own entries (`build_digest::digest_tree_from_entries`, proven equal to `digest_tree`), fetching only root-level files so `--version` honors toolchain pins; hits return without further downloads, and on a miss the files on disk must hash to the same key before the result is stored. Separately, transferred files carry an `executable` flag (protocol `Entry`, default false, not part of keys) restored on the worker and on install — remote-built Linux binaries were not executable. Measured effect: hits went from ~216 s to ~1.1 s (`docs/benchmarks/2026-11-13-remote-cache.md`).

### D-021: A cargo build's input is the whole project (minus outputs and metadata)
**Status:** Adopted 2026-11-13 (P2.4), after remote execution exposed two undeclared inputs: building one package makes cargo load the whole workspace (every member manifest, target-inference files, every locked dependency's manifest), and Rust code can read any project file at compile time (`include_str!`, build scripts — Ant's own crates do). Every cargo action therefore declares the whole project top-down except the target directory, `.ant/`, `.git/`, and output directories Ant created; a symlink keeps the plan uncacheable; files outside the project remain undeclarable and fail closed remotely. Consequence: any file added to the project changes the key (it could be read). A new option `granularity=workspace` emits one `cargo build --workspace` action, which compiles dependencies once — the right shape for remote jobs. This also corrected earlier per-member local keys, which were incomplete.

### D-020: Fully declared cargo builds are cacheable; workers key on their own toolchain
**Status:** Adopted 2026-11-13 (P2.4). The cargo adapter marks actions `cache_policy: eligible` exactly when every non-member package lives inside the project (vendored or path) and `Cargo.lock` exists; such actions pin a workspace-local `CARGO_HOME` so undeclarable user-level cargo config cannot change them. `rust-toolchain(.toml)` is an input. Remote workers replace the plan's client-observed toolchain identity with the toolchain they actually run (argv[0] resolved on the worker's PATH: cached digest + `--version` in the workspace, digest alone for tools without `--version`); unresolvable programs keep the action out of the cache.

### D-019: Shared remote cache — proven on sandboxed Linux workers, path- and time-independent keys
**Status:** Adopted 2026-11-13 (P2.3). Remote cache keys must match across jobs, checkouts, and machines, but local keys include the workspace path and input modification times. Rather than weakening local keys, the worker controls its environment: it writes every input with a normalized mtime (so metadata is a deterministic function of content) and mounts each workspace at a fixed in-sandbox path (`/tmp/ant/ws`, via `PreparedAction::sandbox_mount`), which makes content-only input digests a complete key (`ExecutionFingerprint::remote_worker_sandboxed`). Only sandboxed Linux workers (D-018: no network, write-confined) may store entries, and only for blocker-free keys; clients and viewers can never write, so client compromise cannot poison the cache, while worker hosts and tokens are trusted (documented). The lookup happens on the worker before executing, so the same job can be satisfied without running. Local (non-remote) keys keep path and mtime sensitivity; reusing local results across checkouts is not claimed.

### D-018: Linux sandbox = bubblewrap with every namespace unshared; it may declare network isolation
**Status:** Adopted 2026-11-13 (P2.2), following the owner's choice to keep proof-based reuse and get speed from Linux workers. On Linux, `--sandbox` runs actions under bubblewrap (`--unshare-all --die-with-parent --new-session`, read-only `/`, private tmpfs `/tmp`, fresh `/dev`/`/proc`, the workspace bind-mounted read-write). The empty network namespace blocks connections and name resolution alike — stronger than the Windows account mode (D-013, where DNS leaks) — so this executor declares `sandboxed` and `network_isolation` (`ExecutionFingerprint::local_namespace_sandboxed`, chosen per platform by `local_executor::sandboxed_fingerprint`) and opens the cache gate with no elevated setup. bubblewrap was chosen over hand-written namespace FFI (the workspace forbids `unsafe`) and over containers (image lifecycle, startup latency): it is a small, widely deployed setuid-free tool (Flatpak's sandbox). A per-process preflight proves the sandbox can be created and fails closed with actionable advice (missing package; Ubuntu's AppArmor userns restriction). Accepted limits: host reads are not confined (the network is), the kernel is shared, memory caps remain Windows-only. Workers on Linux therefore produce provable results cheaply — the basis for the shared remote cache (next P2 slice).

### D-017: Front-door behavior for `ant build` / `ant init`
**Status:** Adopted 2026-11-13 (P1.1). `ant build` is zero-configuration: detection picks the adapter (ambiguity is resolved once with `ant init --adapter`, never guessed), plans are generated in memory and kept at `.ant/plan.json`, all cores are used, and progress is rendered for humans from the event stream while the engine's `key=value` lines stay available behind `--verbose` (and unchanged under `ant run`). Builds are **release by default** (`--dev` for debug) because the product's purpose is producing shippable output. Deliverables are chosen by each adapter (`BuildAdapter::artifacts`: cargo binaries, not intermediates; nothing is claimed where the adapter cannot know, e.g. CMake targets) and copied into `dist/`, which Ant only writes when it created it (marker file) — user files are never overwritten. `ant.toml` is optional, parsed with the `toml` crate (1.2; the format developers already use for Cargo and Bun), strict about unknown keys. Toolchain identity digests are cached per user by path/size/mtime (`toolchains.json` in the user cache directory): re-hashing `node.exe` (85 MB) cost ~6.6 s per build and dominated plan generation; the trade-off (a binary replaced with identical size and preserved mtime is not re-hashed) is the same as make's and is documented.

### D-014: Remote execution v1 — own minimal protocol, synchronous HTTP, TLS at a proxy
**Status:** Adopted 2026-11-13 (T4.1–T4.3). ### D-013: Network isolation by dedicated sandbox account; the cache gate opens only under it
**Status:** Adopted 2026-11-13 (T2.9–T2.10), implementing D-009 option A. ### D-011: Resource requests are admission weights, FIFO-admitted, clamped, and excluded from the action key
**Status:** Adopted 2026-11-13 (T1.17). Actions may declare an optional `resources` request (`cpu` slots, default 1; `memory_mb`, default undeclared). The parallel scheduler treats `--jobs` as CPU-slot capacity and `--memory-mb` as an optional memory budget, and admits ready actions in strict FIFO order — no backfill past a head that does not fit — choosing starvation freedom and predictability over peak utilization (a backfilling policy needs aging or reservations to stay starvation-free; revisit with measured workloads in the benchmark lab). Requests above total capacity are clamped with a printed note rather than rejected, so plans stay portable across machines and `--jobs` values. Requests are promises by the plan author, not measured or enforced limits (runtime enforcement, e.g. job-object memory limits, is a separate future slice). Resources cannot affect outputs and are therefore excluded from the action-key candidate; absent requests are omitted from serialization so existing plans and adapter output are unchanged. **Addendum (T1.19):** `--enforce-memory` (opt-in, Windows) turns a declared `memory_mb` into a hard job-wide cap; without the flag requests remain admission weights. `cpu` is never enforced at runtime.

### D-007: Truthful platform fingerprinting via `os_info`, and the Windows sandbox approach
**Status:** Adopted 2026-11-12. `os_info` (3.15.0, build-digest) captures the running OS version so the action key records the platform version as a measured fact instead of leaving a permanent blocker; it is the same crate Cargo itself uses for its user agent (83M+ downloads, maintained). Additionally, research into Windows sandboxing (recorded in `docs/sandbox/windows-design.md`) establishes the intended approach: restricted tokens with per-root restricting SIDs plus scoped NTFS ACL grants and job objects — not AppContainer first — with network enforcement treated as a separate open problem because restricted tokens cannot prevent network access for same-user code. A future low-level FFI crate may carry audited `unsafe` only by explicit decision excluding it from the workspace lint inheritance. **Implemented (2026-11-12):** the `ant-sandbox-win` crate realizes this design — `CreateRestrictedToken` with `DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICT`, a deterministic `S-1-5-21-…` capability SID derived from `SHA-256("ant-sandbox-cap-v1\0" || canonical workspace path)`, an idempotent ACL grant on the workspace root (with post-apply verification so FAT/exFAT fail closed), a permissive default DACL, `SeChangeNotifyPrivilege` enabled, `lpDesktop = winsta0\default`, and a kill-on-close job object for descendants — and is wired into `ant run --sandbox`. `ExecutionFingerprint::local_sandboxed` truthfully declares `sandboxed: true` + `metadata_fingerprinting: true`; `network_isolation` stays false, so cache reuse remains gated by D-003.

### D-008: `windows-sys` FFI for `ant-sandbox-win`, with an audited lint-inheritance exception
**Status:** Adopted 2026-11-12. The Windows sandbox is built on the `windows-sys` 0.59 raw FFI bindings (features `Win32_Foundation`, `Win32_Security`, `Win32_Security_Authorization`, `Win32_Storage_FileSystem`, `Win32_System_Threading`, `Win32_System_Console`) — the same bindings the Rust for Windows project ships, with broadest reuse and no third-party security-boundary crate. `zagens-windows-sandbox` (1065 downloads, a single small publisher that ships its own runner binaries) was evaluated and rejected as too immature to trust as a security boundary. `ant-sandbox-win` deliberately does **not** inherit `[lints] workspace = true`, because the workspace-wide `unsafe_code = "forbid"` discipline cannot express the audited FFI boundary this crate owns; every `unsafe` block in the crate carries a `SAFETY` comment and the public API exposed to the rest of the workspace is safe Rust. The crate-level audit contract and honest limitations (this is a first-line write-confinement defense against accidental escape, not a hardened adversarial boundary; world-writable locations remain writable; network stays unrestricted) are documented in `docs/sandbox/windows-design.md`. The design is adapted with attribution from OpenAI Codex `codex-rs/windows-sandbox-rs` (Apache-2.0).

### D-009: Network isolation requires a dedicated sandbox user + elevated setup; keep `network_isolation = false` and the cache gate closed
**Status:** Adopted 2026-11-13. Investigation in `docs/sandbox/network-isolation.md` established with primary-source evidence that: (1) adding WFP filters or firewall rules is administrator-gated (`FWPM_ACTRL_ADD`/`ADD_LINK`; Microsoft docs), so per-run non-elevated enforcement is impossible; (2) the mechanism proven by both shipped Windows sandboxes (OpenAI Codex, `zagens-windows-sandbox`) is firewall/WFP rules scoped by `FWPM_CONDITION_ALE_USER_ID`/`LocalUserAuthorizedList` to a **dedicated local sandbox account** provisioned by an elevated one-time setup, with the child running as that account; and (3) that scope cannot match Ant's restricted-token capability SIDs, because the user SID is unchanged by `CreateRestrictedToken`. Therefore Ant keeps `network_isolation = false` for all executors today; `network-isolation-unavailable` remains a live blocker; cache lookup/store/reuse stay unwired per D-003 (superseded 2026-11-13 by the T2.8 addendum: mechanics are now wired behind the blocker gate, which this decision's outcome keeps closed); and policy-only controls (hosts/proxy/env) are rejected as dishonest for cache gating. The dedicated-sandbox-user approach (elevated `ant sandbox setup`, DPAPI-protected credentials, idempotent read-back-verified rules, `LocalPolicyModifyState` fail-closed validation, per-machine network granularity with per-workspace filesystem granularity) is documented as the future implementation slice; AppContainer remains an opt-in future mode and `Experimental_CreateProcessInSandbox` is re-evaluated before M4. **Addendum (2026-11-13):** the dedicated-sandbox-account path is implemented as D-013; `network_isolation` is true only for that executor.

### D-010: Adapter contract is in-process; Cargo is the first adapter; generated actions stay non-cacheable
**Status:** Adopted 2026-11-13 (updated T3.4). The adapter contract (`build-adapter`, T3.1) is an in-process trait — `detect` + `generate` producing the canonical `build-graph::PlanFile` — wired into `ant adapt`; an external adapter protocol can be added later without breaking this contract because adapters emit the same plan-file format the run path loads. Two ecosystems are landed, each chosen on the research-required feasibility ground (T0.4: "choose based on actual user demand and feasibility; the spec's candidate list is not itself priority evidence"): **Cargo** (T3.2: `cargo metadata` is a stable offline-friendly JSON API and real adapt → run → artifact verification is possible) and **npm** (T3.4: `node`/`npm` are present in the development environment, so real adapt → run → artifact verification against a TypeScript project is possible; feasibility probed before implementing — cmake/make/msbuild were absent). Generated actions use `cache_policy: never` by construction: where dependency content cannot be declared as an input — cargo registry sources live outside the workspace; the installed npm `node_modules` tree is derived, not source — under-declared inputs must never claim cache eligibility (D-003 spirit). Toolchain identity is captured truthfully from the resolved executable (cargo for cargo; `node` for npm, because `npm` is a script, not an executable). The npm adapter declares no outputs in v1 (npm has no standard layout — unknown layouts are omitted, not guessed, per the honesty rule) and handles the Windows `npm.cmd` batch-shim spawn issue via `cmd /C npm run build`. **T3.5 addendum:** without `--adapter`, `ant adapt` selects an adapter only when exactly one detects the project; no ecosystem priority is invented (ambiguity fails asking for `--adapter`), and detection errors fail closed. Honest v1 limitations (cargo default `target` layout; npm no declared outputs; npm monorepos unsupported; full dependency resolution required; platform-native path separators) are documented in `docs/cli/adapters.md`. **Batch C addendum (T3.6–T3.11):** adapters accept adapter-defined `--option KEY=VALUE` settings validated before any side effect (the one shared-contract change: `generate` takes `&AdapterOptions`; the plan-file format is unchanged); cargo maps the `release` profile and in-project target directories (outside fails closed; non-default dirs are pinned via `CARGO_TARGET_DIR` because the child environment is cleared) and declares in-project dependency sources (vendored crates, non-member path deps) plus `.cargo/config.toml`, which makes `cargo vendor` the verified hermetic path for registry dependencies under `--sandbox`; npm generates one action per workspace package with a build script and declares outputs only on the user's explicit `outputs=entry-points` assertion, because no `package.json` field states what a build produces; a third adapter, CMake, was added on the same feasibility ground (VS-bundled CMake + MSBuild verified adapt → run → artifact; not sandbox-compatible with the VS generator). Every generated action remains `cache_policy: never`.
