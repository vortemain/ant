# Agent handoff guide

## Goal
Build a trustworthy local-first build engine that can grow into self-hosted remote, hybrid, distributed, managed, and enterprise execution. The attached master specification is a user-provided requirements source; it is not evidence that any capability has already been implemented.

## Before taking ownership
1. Read `README.md`, `docs/architecture.md`, `docs/plan.md`, and `docs/requirements-traceability.md`.
2. Inspect repository state and preserve existing edits. Do not assume the repo is clean.
3. Find the active milestone and its acceptance criteria in `docs/plan.md`.
4. Confirm relevant toolchain versions and current tests/build state before changing code.
5. Update the decision log and traceability entries when changing a contract or scope.

## Working agreements
- Keep one canonical contract per concept. Coordinate changes across dependents and document migration implications.
- Prefer a complete, reviewable vertical slice over disconnected crates or UI mockups.
- Do not mark capabilities supported until end-to-end behavior, failure handling, security, observability, docs, and applicable validation exist.
- Treat project build code and plugins as untrusted. Default to least privilege; do not make cacheability or hermeticity assumptions.
- Never put credentials in ordinary action metadata, logs, fixtures, or cache keys. Secret values must not cross trust boundaries as plain environment metadata.
- Use stable Rust by default. Keep dependencies justified and centralized. Avoid premature crate splitting.
- Update this handoff guide when repository workflow or ownership conventions change.
- Do not claim tests, benchmarks, compatibility, security, or deployment succeeded unless actually verified.

## Ownership handoff template
For each work item, record: owner; files/contracts owned; dependencies; acceptance criteria; validation performed and result; known risks; next action. Avoid parallel edits to the same contract files unless explicitly coordinated.
